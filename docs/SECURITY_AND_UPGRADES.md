# Safe upgrades and capital isolation

## Current vault: deliberately not upgradeable

`contracts/src/AgentVault.sol` uses a constructor, `immutable owner` and an explicitly restricted ERC-20 transfer permission mechanism. `VaultFactory.createVault()` deploys `new AgentVault(msg.sender)` directly. There is **no EIP-1967 proxy** around this vault and no UUPS upgrade function. Describing it as upgradeable would be incorrect. The vault is a local/testnet transfer-isolation prototype, **not** a confidential smart account or a live trading vault. Never silently wrap or convert deployed capital contracts into proxies: doing so would change trust, storage and recovery assumptions.

## Separate upgradeable public research-policy reference

The new `contracts/src/AgentSafetyPolicy.sol` uses the **installed pinned OpenZeppelin 5.6.1 libraries** `UUPSUpgradeable`, `Ownable2StepUpgradeable`, and `Initializable` with an EIP-1967 proxy in the Foundry tests. It keeps its own ERC-7201 namespaced storage, locks its implementation initializer, and uses two-step ownership transfer.

Its protocol-level **public research** settings include max slippage basis points, max model-research allocation basis points and minimum public pool liquidity. They do not grant execution and are not individual users' private strategies. `assessResearch()` returns two booleans: whether the public research parameters are within the configured screen, and **`executionAllowed=false` always**. The contract **does not hold tokens, move funds, approve a wallet, manage ciphertext, mint assets, or replace AgentVault**. The web, SDK and MCP interfaces have not been told to trust it as an on-chain authorization oracle.

## Governance and upgrade design

Only its current owner can schedule an implementation upgrade; the new implementation must have deployed code and its exact `codehash` is pinned to the schedule. The schedule must wait **at least 48 hours**; execution is invalid after a further **7-day expiry window**. The owner can cancel, and completed upgrades consume the schedule. Pending upgrades are automatically **invalidated when ownership changes**, so a new owner does not inherit an unseen queued implementation. Direct implementation UUPS upgrades are rejected; incompatible new implementations are rejected by OpenZeppelin's UUPS/ERC-1822 compatibility checks; the implementation is locked against initializer takeover. `renounceOwnership` is disabled to avoid accidental permanent loss of the policy-management account.

These are useful controls, but they **do not make any administrator-operated upgrade trustless**. A future upgrade might add unsafe behavior if approved by an authorized key. A production deployment requires an externally reviewed and appropriately configured **multisig / timelock governance**, off-chain upgrade proposal review, verified source code and storage layout checks, incident rollback/response playbooks and user-facing disclosures. No upgrade or deployment was broadcast to a public chain in this milestone.

`contracts/test/AgentSafetyPolicy.t.sol` exercises proxy initialization, owner-only settings, the nonexecuting research screen, delay/cancellation/expiry, wrong implementation, UUPS incompatibility, successful post-delay upgrade with storage preserved, and two-step owner transfer invalidating queued upgrades. The test-only V2 implementation is not intended for production deployment.

## Emergency-stop guardian (November 11, 2026)

The research-policy owner can appoint or revoke a separate **pause-only guardian** with `setEmergencyGuardian(address)`. The guardian can invoke `emergencyPause()` but cannot resume research screening, change risk limits, schedule upgrades, manage ownership, or transfer assets. Only the owner can resume with `setResearchPaused(false)`. On completed ownership transfer, the old guardian assignment is automatically cleared and the new owner must explicitly designate a guardian again. The role is optional (zero address disables it), and all operations emit events.

The `emergencyGuardian` field is **appended** to the ERC-7201 `SafetyStorage` struct; earlier fields are not rearranged. Foundry tests reject unauthorized guardian calls, check owner-only recovery and upgrade scheduling, verify ownership-transfer revocation, and preserve the guardian assignment through an authorized UUPS V2 upgrade. This is a stop for **research-policy screening only**: it does not halt any external trading system, vault, wallet, MCP host, or Zama contract because none is attached to this policy. A production response still needs off-chain incident monitoring and an independently reviewed governance design.

## Hard requirements before live agent finance

Financial safety cannot be reduced to UI styling or a single DEX market score. Before actual confidential autonomous trading: independently verify Zama FHE ciphertext lifecycle and ACL grants; implement consented smart-account session policies with approved targets/selectors, token budgets, expiry, nonce replay protection, transfer loss caps and immediate revocation; prove swaps through independently verified encrypted venues; keep job and transaction journals with chain finality reconciliation; test upgrade and emergency-pause governance; commission independent security review. On-chain and off-chain risk controls must reconcile rather than trusting model-generated assertions.

## Aggregate agent token budget — November 11, 2026

The **immutable, development-only public** `AgentVault` now enforces an owner-specified per-token aggregate UTC daily limit across **all authorized agent addresses**. Each token starts with a zero limit, so authorization alone cannot spend until the owner explicitly calls `setTokenDailyLimit(token, amountInBaseUnits)`. Zero also immediately halts that token's agent transfers. This limit is independent of per-agent/per-token limits, nonce, fixed recipient, pause and expiry.

`tokenBudgets(token)` contains the daily cap, spent amount and recorded UTC day. `executeTransfer` checks both the specific agent and this aggregate cap **on chain** before the token call; revert rolls back the counter and nonce. The aggregate counter is **not reset** by granting another agent permission, revoking/re-authorizing an agent or raising/lowering the cap. A fresh UTC day resets usage on the next successful transfer. Reducing the cap below already-consumed usage blocks new transfers until the following UTC day or an owner-approved increase. An owner-controlled withdrawal is not agent spending and is not counted against this cap. Values are token base units (no floating point). Independently configured token limits cannot be pooled or converted based on external price feeds.

The SDK snapshots the global cap at the same block as the agent permission, pause, balance and nonce. A simulation reports `TOKEN_DAILY_BUDGET` if the aggregate cap is absent or exhausted, then independently performs an `eth_call`. The vault owner UI reads this counter and requires an explicit cap rather than inventing defaults. The Anvil deployment script sets an explicit local-only budget for its test fixtures.

**Compatibility and scope:** this changes `AgentVault` runtime bytecode and the `VaultFactory` creation code; the client intentionally matches the regenerated deployed runtime. Previously deployed development vaults are NOT upgraded, and older bytecode will fail the new SDK's identity check until a deliberate versioned legacy-read strategy exists. Never migrate capital silently or claim a production upgrade. The `AgentSafetyPolicy` UUPS research registry is separate and does not govern vault transfers. This shared public-token limit is not an FHE trading, portfolio-value, cross-asset exposure, or mainnet control. Independently audited confidential smart-account authorization remains necessary before financial launch.

Negative tests cover two-agent aggregation, reauthorization bypass attempts, zero/reduced cap, independent tokens, UTC day rollover, unauthorized configuration, arithmetic fuzzing and rollback on hostile token behavior. The local-browser test uses an actual Anvil vault to set cap zero, observes a denied simulation, restores the cap and observes a passing simulation; its injected wallet is a test transport, not external-wallet or Sepolia proof.
